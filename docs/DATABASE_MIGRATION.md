# Database Migration: EF Core → Drizzle ORM

## Summary

| Item | Before | After |
|---|---|---|
| ORM | EF Core 10 + Npgsql | Drizzle ORM (`drizzle-orm/node-postgres`, `pg`) |
| Schema source | C# entities + configurations | `apps/web/src/lib/db/schema.ts` |
| Migrations | `apps/api/.../Migrations` (EF) | `apps/web/src/lib/db/migrations` (drizzle-kit) |
| History table | `public.__ef_migrations_history` | `drizzle.__drizzle_migrations` (the EF table is kept, untouched) |
| Apply | `dotnet run -- migrate` | `npm run db:migrate` |

**No table, column, index or constraint was renamed, retyped or dropped.**

## How the schema was carried over

1. `drizzle-kit pull` introspected a database created by the EF migration `20261031082752_InitialCatalogue`. The result was hand-cleaned into `schema.ts`: typed enum columns, `Date` timestamps, numeric values as JS numbers, and explicit PK names (`pk_*`) matching EF.
2. **Fidelity check:** Drizzle's own SQL for the schema and EF's SQL were applied to two empty databases and compared with `pg_dump --schema-only`. They were identical except for one index property Drizzle cannot express: `NULLS NOT DISTINCT` on `ix_variant_prices_variant_id_market_id_region_code_price_type`.
3. Therefore `0000_baseline.sql` is **EF's exact generated SQL** (minus EF's own history table). New databases and adopted EF databases are identical, including that index.
4. `0001_sessions.sql` (generated by drizzle-kit) adds the `sessions` table, an additive change. drizzle-kit produced only this table, confirming its snapshot matches the baseline.

## Ownership hand-over (adopting an existing EF database)

`npm run db:migrate` (`lib/db/migrate.ts`):

1. Creates `drizzle.__drizzle_migrations` if missing.
2. If it is empty **and** `public.__ef_migrations_history` exists, it requires that the EF history is exactly `[20261031082752_InitialCatalogue]`. Anything else aborts with an error for manual review. It then **records** the Drizzle baseline (hash + timestamp) as applied, without executing it.
3. Runs Drizzle's migrator, which applies only migrations newer than the baseline (currently `0001_sessions`).
4. Upserts reference data (market `IN`, 35 specification definitions, roles). This is idempotent.

Verified on a real EF-created database (9 models, 301 spec values and a staff user before and after), and covered by `tests/integration/adoption.test.ts`. Re-running is a no-op.

## Safety rules for future migrations

- Change `schema.ts`, run `npm run db:generate`, then **read the generated SQL** before committing it.
- Never edit an applied migration. Add a new one.
- Destructive changes (drop/rename/retype) need a written plan: add the new column, backfill, switch reads/writes, then drop in a later release.
- Production: run `npm run db:migrate` as a release step with a backup or point-in-time recovery available. Never run `db:seed` (it refuses when `NODE_ENV=production` or `MOTOSCOPE_ENV=production`).
- Unused legacy Identity tables (`user_claims`, `user_logins`, `user_tokens`, `role_claims`) remain in the schema but are not declared in Drizzle. Drop them only through an explicit, reviewed migration.

## Behavioural notes

- `numeric` columns are mapped to JS numbers (values ≤ 12 significant digits, so no precision loss).
- Timestamps are written with millisecond precision (EF wrote microseconds). Existing values are unchanged; responses serialise milliseconds.
- `xmin` is read as `xmin::text` and compared as `::xid` for optimistic concurrency, the same semantics as EF's row version.
